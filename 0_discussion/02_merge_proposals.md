## 一、P0:斷鏈修復類(先做,順序最高)

### 1. 讀回結果落地 `.lv_cache` 標籤覆蓋層 + 變更日誌

- **現狀**:`apply_readback` 只改記憶體中的 `records[idx]["label"]`(labeling_handoff.py:378-413,實際寫入在 400-413),而「匯出」工具讀的是磁碟上的 label 檔——標註者在 ANnoTation 修正的標籤**進不了訓練集**,LV 重 Run 即蒸發,整輪標註等於白做。
- **提案**:讀回結果落地到 `.lv_cache` 標籤覆蓋層(不碰使用者資料集,遵守 [[no-dataset-writes]]),附 append-only 變更日誌(舊標/新標/annotator/時間戳);匯出工具加「含讀回修正」選項。
- **動機**:這是全系統最高優先缺口,AL 迴圈「標→訓」斷鏈的根因。
- **風險**:覆蓋層與盤上 label 的優先序語義要定義清楚;匯出路徑需回歸測試。
- **反方意見**:無異議——四方一致,守成派亦列為「斷鏈不是重組」的最高優先。
- **主席裁決**:**採納**。同時化解 CV 提案最高缺口與反方審計否決項。
- **優先序/定位**:**P0/新需求須立案**(08–13 規格均未涵蓋,須走 U-Net 立案)。

### 2. 統一送標正典文案(刪「不用回 LV」矛盾)

- **現狀**:「不用回 LV」文案 7 行(app.py:2412, 2712, 2787, 3289, 6336, 7205, 7234)與「📥 標註回饋」分頁的「標完…回來這裡按『套用讀回結果』」(app.py:7256-7257)直接矛盾;工程師每次都要重想哪條才是正典。
- **提案**:統一為單一正典「送出 → ANT 標 → 回 LV 套用」,刪除所有矛盾文案。
- **動機**:兩套互斥指引並存 = 使用者無法建立正確心智模型;讀回落地(第 1 項)後「不用回 LV」更是錯的。
- **風險**:低(純文案),但 7205/7234 是 E2E 可見字串。
- **反方意見**:支持;條件 = 同 PR 掃 `tests/e2e` 更新文字選擇器。
- **主席裁決**:**採納**(附反方條件)。
- **優先序/定位**:**P0/既有元件重排**(文案)。

### 3. 功能地圖清理 + Compare 死碼/demo 鈕

- **現狀**:(a) 「✨ 功能地圖」popover 仍教使用者用組考卷/灰帶覆核/評估(app.py:8108-8123,尤其 8116-8121「一鍵送組考卷/灰帶覆核」),但 8098-8099 明確把這三工具擋在工具列外——**假地圖**;(b) `_render_cmp_panel`(app.py:4596)定義後全檔零呼叫,確為死碼;(c) Compare 錯誤訊息指向不存在的 demo 按鈕。
- **提案**:功能地圖全數改指現行出口;刪 `_render_cmp_panel` 死碼;補 Compare demo 鈕。**不刪** handoff 函式(`TASK_ADJUDICATE` 呼叫點 app.py:7642, 7791 在隱藏工具內仍是活契約)。
- **動機**:照地圖找不到工具 = 假地圖;死碼誤導維護者。
- **風險**:低。
- **反方意見**:A2/A5 支持;條件 = 只改文案與確證死碼,結構性移除隱藏工具另案(見第 14 項)。
- **主席裁決**:**採納**(含保留條件)。
- **優先序/定位**:**P0/既有元件重排**。

### 4. pool_registry / round_ledger 開工 + 拆 `read_back` 一詞兩義

- **現狀**:哪些 sha 送過標無登記(無 pool_registry)、這是第幾輪不可追(無 round_ledger)、批次永不結案(`delete_pending` 定義於 labeling_handoff.py:97,app.py **零呼叫**)、sha 不匹配時靜默顯示「沒有變更」(app.py:7292);且 `read_back` 一詞兩義——ANT 端的「已匯出」(014_process.py:63-67,全批標記)與 LV 端的「已套用」互相誤讀。

- **動機**:重複送標無防呆、回合不可追溯、換班即失憶。
- **風險**:跨 repo(ANnoTation 014_process.py)+ nativeApp vendored 雙副本,**三處同步**成本不可低估([[lv-vendored-submodule-sync]])。
- **反方意見**:支持;條件 = 新增狀態值不改名、向後相容、三處同步。
- **主席裁決**:**採納**。開工程序走 CLAUDE.md 閘門,**仍待 User 放行**。
- **優先序/定位**:**P0/M9–M11 已規劃**(規格 08/09 已備)。

### 5. 評估閉環:probe_eval 接 GUI

## 二、P1:加法顯性化類

### 6. 框級 shapes 讀回——分兩段

- **現狀**:讀回只取 `shapes[0].get("label")`(labeling_handoff.py:287-288),detection 任務的框幾何**全丟**,LV 只拿得回一個分類字串。
- **提案**:**分兩段**——第一段:分類字串迴圈先落地(隨 P0 第 1 項讀回落地層);第二段:shapes 幾何讀回,配 13_heatmap_to_boxes(M13 預標框)一起做。
- **動機**:detection 場景的標註成果不該蒸發;但先讓分類迴圈「可審計地轉起來」價值更高。
- **風險**:中;幾何讀回牽動覆蓋層 schema 與匯出格式(COCO/VOC/LabelMe/NDJSON,[[label-format-support]])。
- **反方意見**:反方二主張「先分類、後幾何」,與 CV 提案的第 1 排序相左。
- **主席裁決**:**有條件採納**——採「分段」而非「不做」。
- **優先序/定位**:第一段 **P0**(併入第 1 項);第二段 **P1/已規劃 M13 搭配 + 部分新需求**。

### 7. task 顯式 selectbox

- **現狀**:送標任務以排序語境隱式推導——「離群度排序 = verify,否則 relabel」(app.py:2403-2404),標註者不知道自己被指派什麼任務。
- **提案**:顯式 selectbox,**預設值 = 現行推導結果**,行為不變。
- **動機**:task 語義顯性化是 CV↔標註者協作權責的最低要求。
- **風險**:最低(加法、預設不變)。
- **反方意見**:支持。
- **主席裁決**:**採納**。
- **優先序/定位**:**P1/既有元件重排**(加法)。

### 8. 四態徽章 / round_id / annotator 顯性化

- **現狀**:批次清單只顯示 `n_annotated/n_total`(app.py:7264-7273);annotator 已被讀取(labeling_handoff.py 相關路徑,app.py 材料引 294)、狀態常數已存在(`STATUS_SENT` 等),但 CV 端半盲、User 端全盲。
- **提案**:兩端同步最小顯性化資訊集:round_id(寫入 `_handoff.json`/`_pending.json`)、source·task·一句選樣理由(ANT module_012 呈現)、四態 `sent→annotating→exported→applied` 附未標清單、annotator;sha 不匹配**顯式報錯**(取代 7292 的靜默「沒有變更」);結案鈕接上零呼叫的 `delete_pending`。
- **動機**:「標完了嗎/套回了嗎」目前靠人腦記。
- **風險**:跨 repo 契約 + vendored 三處同步(同第 4 項)。
- **反方意見**:支持(純加法 UI);條件 = 向後相容。
- **主席裁決**:**採納**。
- **優先序/定位**:**P1/已規劃(08/09)+ 小案立案**(預標分數 sidecar 寫入 handoff 為新需求小案)。

### 9. 瑕疵偵測③補「直送 Labeling」鈕

- **現狀**:瑕疵③「挑樣送人工標」只有加入購物車一途(app.py:1968-1970),最該送標的頁面沒有送標出口——名實不符。
- **提案**:補直送 Labeling 鈕,復用 `_send_to_labeling_ui`(app.py:7190)。
- **動機**:縮短最高頻動線(挑樣→送標)一整步。
- **風險**:低(加法);兩條件——送出須用**原圖路徑而非 crop**([[object-export-crop-bug]] 教訓)、widget key 進 anomaly 命名空間。
- **反方意見**:有條件支持,條件如上。
- **主席裁決**:**採納**(附兩條件)。
- **優先序/定位**:**P1/既有元件重排**(加法)。

### 10. 兩套挑樣:後端共用 M11 純函式,UI 各自保留

- **現狀**:Visualize 選樣(純多樣性 FPS)與瑕疵③ 2×2 三訊號矩陣各挑各的,購物車是唯一交會點——兩套 AL 訊號不互通。
- **提案**:**不合併 UI**;11_hybrid_sampler 做成純函式,兩頁後端各自呼叫,加 10_gt_pred_diff 四佇列(FN/FP/混淆/低信心)訊號源。
- **動機**:訊號統一的價值在後端,不在元件;CLAUDE.md「復用不另起爐灶」。
- **風險**:低(UI 不動)。原 UI 合併案風險為中偏高:兩頁 record 空間不同(整圖 viz_records vs 物件級 crop),M7 才修過 confirmed 跨①②索引空間污染;2×2 活在 st.tabs 內,rerun 重置 tab 是已知系統性 flaky。
- **反方意見**:反方一 A4 反對 UI 合併、有條件支持後端共用——被全盤採納。
- **主席裁決**:**有條件採納**(後端共用版;UI 合併版入不做清單)。
- **優先序/定位**:**P1/M10–M11 已規劃**。

### 11. 「📥 標註回饋」擴建為「🔁 標註迴圈」單頁(不加第七工具列項)

- **現狀**:一輪 AL 要跳 6 頁 + 2 個外部動作,狀態靠人腦串;隱藏工具正規化邏輯與工具列耦合(app.py:8096-8099)。

- **風險**:中;「作用中回合常駐顯示」為 09 規格自承缺口,須先補規格。
- **反方意見**:有條件支持;反對新工具列項(肌肉記憶 + 8098 正規化耦合)——條件被採納。
- **主席裁決**:**有條件採納**(落點 = 📥 擴建,與 M9/M12 規格已選落點一致)。
- **優先序/定位**:**P1/既有元件重排 + 已規劃(08–12)+ 新需求須立案**(讀回落地層、回合常駐顯示、預標 sidecar 寫入 handoff、評估遺產併入回合報表四項為新缺口)。

## 三、P2:文案收斂與殘骸處置

### 12. 三個「匯出」撞名——收斂稱謂,不造新名

- **現狀**:「匯出清單」面板(app.py:3241,送整車鈕 3286)、工具「匯出」(app.py:1123/1129)、購物車內匯出 CSV/ZIP 三名並存;同一 list 兩入口;1129 行本已並列「策展購物車/匯出清單」兩名。
- **提案**:不採原案更名(「🛒 購物車」「組訓練子集」);改為**文案收斂到既有一名「匯出清單」**,其餘處所統一稱謂。
- **動機**:三名並存是認知負荷;但再造第三名是加劇而非解決。
- **風險**:低(收斂版);原更名案風險高——「匯出清單/送整車」在 tests/e2e 出現 8 處、涉 10 檔,文字選擇器全斷;app.py:8096-8097 現存的「匯出子集→匯出」session 正規化正是上次更名留下的永久疤痕。
- **反方意見**:反對更名、支持統一稱謂——被採納。
- **主席裁決**:**有條件採納**(收斂版;更名版入不做清單)。
- **優先序/定位**:**P2/既有元件重排**(文案)。

### 13. 行話改寫——只動 caption/help

- **現狀**:「桶①佔比」「B 的角色/採礦池」等行話,面板需三段 caption 自我解釋。
- **提案**:caption/help 改為「可偵測性檢查」「候選池/參照集」等可解語彙;**widget label 不動**(「桶①」有 E2E 測試檔命中)。
- **動機**:降低領域專家上手成本。
- **風險**:低(只動說明文字);widget label 若動則 E2E 斷。
- **反方意見**:有條件支持,條件 = 改 label 前先 grep tests/e2e——採納為「label 緩做」。
- **主席裁決**:**有條件採納**。
- **優先序/定位**:**P2/既有元件重排**(文案)。

### 14. 隱藏三工具處置:回歸新迴圈,不平行重造

- **現狀**:組考卷/灰帶覆核/評估被工具列正規化擋掉(app.py:8098-8099),但殘留 4 個 handoff 函式,其中 `TASK_ADJUDICATE` 呼叫點(app.py:7642, 7791)仍是活契約。
- **提案**:評估 → 併入 M10 gt_pred_diff 回合報表 + M12(含漏抓畫廊與共識校尺遺產);灰帶裁決 → 掛回 📥 分頁(TASK_ADJUDICATE 還活著);組考卷 → 降級為 kappa 計算,多人標由 ANT 派發。
- **動機**:別解隱藏也別平行重造;新迴圈的 recall 不能建在未驗證真值上。
- **風險**:中;刪除/降級是 ROADMAP 層決策。
- **反方意見**:方向對,但須 **PO 先記決策日誌**,PG 不得先動;現階段只做第 3 項的文案清理。
- **主席裁決**:**有條件採納**(結構性移除緩做,待 PO 決策日誌 + M10/M12 落地)。
- **優先序/定位**:**P2/已規劃(M10/M12)+ ROADMAP 決策**。
