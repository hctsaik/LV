# PRD:大資料主動學習可用性 + 離線監看選樣服務

對應 User 需求:[1_user_needs/al_scale_offline.md](../1_user_needs/al_scale_offline.md)
設計素材(預聚合,非契約):[AL_SCALE_AND_OFFLINE_SERVICE_PLAN.md](../AL_SCALE_AND_OFFLINE_SERVICE_PLAN.md)
里程碑:**M9**(大資料 GUI 可用性)+ **M10**(離線監看服務)—— 瑕疵/主動學習 feature 收斂後的**新能力**輪次(起新輪)。

## 三行自問(缺一不放行)

- **誰會用**:手上資料量很大(數萬~十萬張)、且資料夾**持續進新圖**的品管工程師/資料集管理者;
  一天只願花 ≤30 分鐘標註,不可能一直開著互動畫面等它算。
- **不做會怎樣**:資料一多,現行「整條 pipeline 綁在 Streamlit 互動 session 同步跑完」→ 畫面卡死/等數小時、
  關掉就重來、每天新圖得手動重跑且自己記哪些看過 → 這群人**實質不能用**主動學習,退回人工一張張看。
- **成功的可觀察判準(直接餵給 /pm 當 AC 來源)**:
  1. 大資料「掛著慢慢跑」:分批處理,關掉 app 再開能**從上次進度續跑**(不從 0)。
  2. 「邊跑邊看」:跑到部分完成度即可看**暫定 Top-K**,畫面**明講**「暫定,已處理 x%」。
  3. 「只給要的」:設定「一次看約 **100** 個」,畫面直接給排好的 100 個佇列 + 分數分佈小圖,**不渲染全量散點**、不卡。
  4. 離線服務:指定一個(持續更新的)資料夾 → **不開互動畫面**也能自動選出「最該標註/釐清的前 100 個」。
  5. 增量:服務**只處理新的/變更的**;昨天看過的、已標過的,今天**不再重複出現**。
  6. 設定可攜:在 GUI 設定服務(目標/資料夾/K)→ 能**匯出成一份設定檔**,服務照它跑;改設定只在 GUI 改再匯出。
  7. 不碰原始資料:全程對監看/來源資料夾**只讀**,跑完原始資料夾**零位元組變動**。
  8. 消費閉環:掛著跑或服務挑出的,最後都在**一個佇列**逐張看縮圖+**人話理由**+做決定,標註**下輪生效**(不重複煩)。
  9. 服務健康可見:打開 GUI 若服務太久沒成功跑,**顯眼提示上次成功時間**。

## 目標與成功指標

- 讓主動學習/瑕疵偵測在**數萬~十萬**筆物件下仍**可用**(可掛著跑、可續跑、可只看 Top-K)。
- 讓「選樣」能**離線、自動、增量**地在持續更新的資料夾上跑,產出**可消費的標註佇列**。
- 衡量(可觀察):
  - 首跑中斷後續跑,**已處理批次不重算**(以測試層的假 embedder 呼叫計數證明)。
  - 標註模式下**不計算投影、不渲染全量散點**(大資料仍秒開佇列+直方圖)。
  - 服務跑一輪後,佇列 = 「新資料的 Top-K、排除已標註」;隔輪標註反映在佇列(標過的消失)。
  - 全程來源資料夾 mtime/檔案清單快照**零變化**。

## 產品憲法(不可違反約束 —— 下游任何階段發現矛盾,走反向閘門回報,不准就地繞過)

1. **一個引擎、兩個前端**:分批選樣引擎只有一份純邏輯模組;GUI 內嵌跑它、離線服務也跑它。禁止各寫一套 pipeline。
2. **佇列是核心產出物**:產品輸出 = 排好序、附**人話理由**、可消費的標註佇列。散點圖降為(可選)探索視圖。
3. **顯示預算三模式**:標註(免投影、只佇列+直方圖)/ 探索(抽樣散點,含強制納入 Top-K 與已確認)/ 完整(小資料=現況)。依量自動建議、可改。
4. **「已存模型」是 GUI↔服務唯一契約**:服務只**讀** GUI 一鍵存出的模型目錄;版本**顯式**升級(GUI 重存→服務下輪才用新版);**服務絕不自己重訓/改模型**。佇列項目蓋模型版本章。
5. **單寫者原則**:服務寫 queue/state,GUI 只 **append** 寫 labels;服務下輪合併(標過的移出待辦)。兩邊永不寫同一檔。
6. **絕不寫使用者資料夾**(既有鐵則 [[no-dataset-writes]]):工作區/checkpoint 放 `.lv_cache/` 或使用者另指定的**非來源**目錄;沿用 `anomaly_bank_store.assert_safe_bank_dir` 防呆模式。
7. **run-once + 外部排程,不做常駐 daemon(v1)**:服務提供「跑一輪就退出」;排程交外部(工作排程器/手動/未來平台)。GUI 提供「立即掃描一次」(in-process 跑,重用引擎與進度 UI)。
8. **分批正確性**:凍結模型下逐項評分獨立 → 分批+合併數學上安全;任何**全域運算**(分群/投影/門檻校準)只能對抽樣、或全批完成後跑。**嚴禁把全域運算塞進單批。**

## 使用者四項拍板決策(已確認,寫入約束)

| 決策 | 內容 | 對設計的意義 |
|---|---|---|
| **K 預設** | **100** | 佇列預設 Top-100;GUI/設定可改。 |
| **版本過期項目** | **重評分**(rescore),不標 stale 擱置 | 模型換版後,舊 pending 以新模型重評分再排序(embedding 有快取,便宜且誠實)。 |
| **服務/GUI 部署** | **v1 同機**;**長期跨機** | v1 假設同一台(工作區走本機路徑);但**架構不可寫死同機假設**——路徑走 config、服務為「設定檔的純消費者」、設定檔可攜(跨機時換路徑即可)。跨機部署本身列 Won't(v1)。 |
| **GUI 設定 + 匯出** | GUI 有 config 設定區,**可匯出設定檔**給服務吃 | GUI 是設定的**唯一編輯面**;匯出產生服務讀的設定檔;服務不自帶設定 UI。此為 **M10 Must**。 |

## 其餘開放問題的 PO 裁決(補齊 plan §7)

- 多 profile 並存:**v1 就做**(工作區天然 per-profile 目錄,成本低)。
- 標註模式自動切換門檻:**5000 物件**(進階設定可調)。
- 監看資料夾 == 建模資料夾:**警告不阻擋**(容許「全量巡檢自己」)。
- 已刪除檔案的佇列項目:**標 stale 並隱藏,不刪**(保留審計)。

## 範圍(MoSCoW)

### M9 — 大資料 GUI 可用性

**Must**
- 分批、可 checkpoint、可**續跑**的選樣引擎(凍結模型下逐批評分,任何時刻給得出「已處理併集」的正確 Top-K)。
- GUI **顯示三模式**(標註/探索/完整),依物件量自動建議(>5000 預設標註模式),可手動改。
- **暫定 Top-K**:跑到部分完成度即可看,畫面明示「暫定·已處理 x%」;中斷後可「繼續上次」。
- 標註模式:只渲染**佇列(預設 Top-100)+ 分數分佈直方圖**,不算投影/不畫全量散點;探索模式抽樣散點(上限例 5000,強制納入 Top-K 與已確認)。

**Should**
- 佇列每項「人話理由」(由分數組成 → 文字模板:很不像正常/模型拿不準/與已標矛盾)。

**Won't(本輪)**:離線服務(→ M10)、跨機。

### M10 — 離線監看選樣服務

**Must**
- **工作區**:一份可持久化的服務工作區(設定/掃描狀態/佇列/標註/每輪摘要/執行鎖),單寫者原則。
- **CLI 服務 run-once**:增量掃描(只處理新/變更檔)→ 用已存模型跑 M9 引擎 → priority+多樣性選樣 → 合併標註(移出已標)→ 物化佇列 → 寫摘要 → 退出。
- **GUI 設定區(④ 監看)+ 匯出設定檔**:profile 新建/編輯(目標三選一人話/資料夾/K/來源類型)、**匯出設定檔**供服務讀;服務狀態卡(上次成功時間/上輪計數/模型版本符不符警告);「▶ 立即掃描一次」(in-process 重用 M9 引擎與進度 UI)。
- **Step③ 佇列消費**:佇列來源切「本次 Run / 監看佇列」;逐張縮圖+理由+三鍵(✅正常/🏷瑕疵選類/⏭略過)→ **append** 標註並即時移出;分頁。
- **版本過期重評分**、**增量只算新圖**、**只讀來源資料夾**、**服務健康呈現**(依上表決策)。

**Should**
- 確認正常累積 → 引導「擴 Normal Bank → 重存模型」(串既有 M5 confirm 流程,服務下輪用新版)。
- GUI「複製排程指令」框(工作排程器一行命令)。

**Could**
- 分數/類別前置篩選(filters)、分數分佈漂移警示。

**Won't(本輪,寫入決策日誌)**
- 常駐 daemon / 檔案系統 watch(用輪詢掃描)。
- 服務自動重訓/自動更新模型(模型版本一律 GUI 顯式升級)。
- 多人並行標註、權限、email/推播通知、跨機部署本身。
- CIM 平台(nativeApp)整合:平台 engine 排程本服務、佇列餵 Labeling plugin(X-AnyLabeling)——**留鉤子不實作**;架構師設計佇列 schema 時參考既有 `scripts/labeling_handoff.py` 保持欄位可對接。

## 模組分解(交給 /architect)

> Tier 判定:三個引擎/服務模組皆有**檔案 I/O 且被依賴** → 依鐵線一律 **Tier B**。
> 但**無 GUI** 者驗收 = 單元 gate **+ 真實檔案系統整合測試**(假 embedder、tmp 目錄),**非**瀏覽器 E2E;
> 只有 **GUI 接線**走 Playwright E2E。此區分請架構師在設計的 AC 段落沿用。

| # | module | 一句話職責 | Tier | 里程碑 | 相依 |
|---|--------|-----------|------|--------|------|
| 08 | `al_batch` | 分批跑「發現→embedding→對凍結模型評分」並可斷點續跑,任何時刻給得出(暫定)Top-K | B | M9 | 既有 `anomaly_tool.run_pipeline`、`active_learning`、`active_loop`、`dino_head`、`anomaly_bank_store`、`safe_io`、`.lv_cache` |
| 09 | `al_workspace` | 管理離線服務工作區的全部持久化(設定/狀態/佇列/標註/摘要/鎖)與增量掃描狀態 | B | M10 | 既有 `model_manifest`(版本 hash 候選)、`anomaly_bank_store.assert_safe_bank_dir` |
| 10 | `al_service` | run-once 編排:增量掃描→08→選樣→合併標註→物化佇列→摘要(CLI) | B | M10 | 08、09、`dino_head`/`anomaly_bank_store`(讀模型) |

GUI 接線(app.py `_anomaly_ui`):M9 三模式顯示+暫定 Top-K+續跑;M10 ④ 監看設定/匯出/狀態/立即掃描 + Step③ 佇列消費 —— 屬**既有 anomaly 整合層接線**,隨對應里程碑做、以**真實 E2E** 驗收,不另立模組。

**拆模組品質自檢**
- **08 al_batch**:① 內聚=「分批評分並可續跑、隨時給暫定 Top-K」(一句,無「以及」)✓ ② 契約=少數函式(`run_batched(...)` + checkpoint 讀寫),相依顯式不成環 ✓ ③ 可獨立驗收=/pm 用假 embedder+tmp checkpoint 驗「分批==一次跑全等」「續跑不重算」「暫定 Top-K 正確」,不依賴 09/10 ✓
- **09 al_workspace**:① 內聚=「服務工作區的持久化與增量掃描狀態」(持久化是單一主題)✓ ② 契約=load/save profile、read/append labels、atomic rewrite queue、scan_incremental、model_version、lock;相依顯式不成環 ✓ ③ 可獨立驗收=/pm 用 tmp 目錄驗 round-trip/增量 diff/原子性/安全目錄/鎖,不依賴 08/10 ✓
- **10 al_service**:① 內聚=「跑一輪離線選樣的編排」(一句)✓ ② 契約=CLI(`run`/`status`/`init`)+ 對 08/09 的呼叫;相依顯式(08、09)不成環 ✓ ③ 可獨立驗收=/pm 用合成資料+假 embedder 驗首輪/增量/閉環/版本重評分/壞輸入/零資料集寫入/併發鎖,不觸真模型 ✓

## 使用者驗收(銜接 User 文件)

- 幾萬張掛著跑 → 關 app 再開 → 「繼續」從上次進度接續(不從 0)。
- 跑到約三成 → 已能看暫定 Top-K,畫面明示「暫定·已處理約 30%」。
- 設「一次 100 個」→ 直接得排好的 100 個佇列 + 分數分佈小圖,不卡、不渲染全量散點。
- 設定一個持續更新的資料夾 + 匯出設定 → 服務(未開畫面時)自跑一輪 → 隔天 GUI 佇列 = 新的、未看過的該看清單。
- 昨天標過/看過的今天不再出現;每項有人話理由;服務太久沒跑會顯眼提示。
- 全程原始資料夾零變動;設定可匯出、服務照設定跑(同機 v1,跨機時換路徑即可)。

## 給架構師的開放問題(需技術判斷才能定)

1. **al_batch 與 run_pipeline 的關係**:是「在 `run_pipeline` 外層分批編排」還是「抽出其內部階段(discover/embed/score)自組」?哪個較不擾動既有契約、且能重用 `.lv_cache` 增量?
2. **checkpoint 格式與續跑判定**:以已處理 path 清單、還是 index 游標?逐批 score 增量檔如何合併?中斷點的原子性如何保證(對齊既有 `_atomic_*`)?
3. **模型版本 hash**:直接重用 `model_manifest.py` 還是新增?版本 = 哪些檔案內容(bank+head+meta)的 hash?
4. **暫定 Top-K 的正確性**:如何在「已完成批次併集」上重算 priority/多樣性而不需重掃全部?diversity 選樣(cluster)在分批下如何處理(對已處理併集重算,還是留到全批完?)——請明確,避免違反憲法 8。
5. **佇列項目 id 與冪等**:id 用什麼(path+bbox+model_version 的 hash?)以確保增量與重評分下**同一物件穩定對應**、標註能正確合併?欄位命名對齊 `labeling_handoff.py` 到什麼程度?
6. **標註模式自動切換與探索抽樣**:>5000 自動切標註模式的門檻放哪(可調)?探索模式抽樣策略(分層?上限 5000?強制納入 Top-K/已確認的作法)?
7. **服務 in-process「立即掃描一次」vs CLI**:GUI 直接呼叫 al_service 的 run 函式(同進程、重用 M9 進度)是否可行、與 CLI 共用同一入口?(憲法 7:不 spawn 常駐)。
8. **跨機約束的落地**:哪些欄位/路徑必須進「可攜設定檔」、哪些是本機衍生(不進設定檔),才能讓「換台機器改路徑即可」成立而不必改碼?
