# 目標工作流與角色邊界

## 建議的 Active Learning 回合

1. **定義本輪問題**：不是只填資料夾，而是選定產品／layer／tool／recipe、目標缺陷、模型版本與成功門檻。
2. **凍結候選池**：建立 pool snapshot，記錄排除規則，避免相同樣本跨輪重送。
3. **診斷並取樣**：依問題使用 anomaly、uncertainty、coverage、diversity、drift 或 confusion 訊號。
4. **送出標註批次**：批次中包含 task、理由、預標、優先序、截止條件與必要 metadata。
5. **ANnoTation 執行**：標註者完成分類／框／遮罩；不確定者送領域專家裁決，而非自行猜測。
6. **讀回與驗證**：檢查完整率、schema、影像雜湊、重複與爭議，將修正持久化並留下變更歷史。
7. **重訓／更新 bank**：只有通過驗證的資料進入新資料版本；normal/golden bank 更新需額外簽核。
8. **比較本輪成效**：看 per-class recall、underkill、overkill、未知率、標註成本與每 100 個標註帶來的增益。
9. **人工決定下一步**：繼續標註、調整策略、回頭修規格或停止；系統可以建議但不應自動拍板。

## 角色不應只寫成 User

| 決策／工作 | 標註／複判員 | 製程／領域工程師 | 品保／產品負責人 | CV 工程師 | 系統 |
|---|---|---|---|---|---|
| 定義 defect taxonomy 與判準 | C | **A/R** | C | C | 留版本 |
| 決定本輪工程問題 | I | C | **A** | **R** | 建立 round |
| 選樣策略與批次 | I | C | I | **A/R** | 去重、配額、說明理由 |
| 執行標註／複判 | **R** | C | I | I | 顯示預標與必要脈絡 |
| 爭議裁決 | R | **A/R** | C | C | 記錄理由與版本 |
| normal/golden bank 更新 | I | **A** | 簽核 | **R** | 不可變更歷史 |
| 模型、閾值與部署候選 | I | C | **A** | **R** | 提供 gate，不自動發布 |
| 是否停止本輪 | I | C | **A** | R（提供證據） | 提示邊際效益 |

`A` 是最終負責，`R` 是執行，`C` 是需諮詢，`I` 是需知會。

## LV 與 ANnoTation 的責任邊界

### VisualLatent 應負責

- 問題定義、pool snapshot、選樣、候選理由與優先序。
- 模型／embedding／bank 版本與回合成效。
- 送標前建立穩定 batch contract。
- read-back 驗證、資料版本化、回合報告與下一輪建議。

### ANnoTation 應負責

- 任務 claim、annotator、開始／完成時間與工作量。
- 分類、bbox、polygon/mask 等標註操作與預標修改。
- skip／uncertain／needs-expert 的顯式原因。
- 多人重複標註、領域專家裁決、標註匯出完整性。

### 兩端共同契約

- `batch_id / round_id / sample_id / task_type / schema_version`。
- `sent → claimed/annotating → submitted → validated → applied` 狀態與時間戳。
- 選樣理由、預標來源、model/bank version、annotator 與 adjudicator。
- read-back 不能只改記憶體；應以 append-only change log 留下 old/new、誰改、何時改、為何改。

## 讓協作更明確的畫面資訊

每個標註批次的標題區應直接回答：

- 這批為什麼被選中？
- 要做分類、驗證、重標還是裁決？
- 誰負責，完成定義是什麼？
- 使用哪個 taxonomy／instruction 版本？
- 目前完成多少，還有哪些錯誤或爭議？
- 回到 LV 後會影響哪個資料版本、bank 或模型？

這比在兩端增加更多自由文字說明更重要。
