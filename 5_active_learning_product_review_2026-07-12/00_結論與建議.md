# VisualLatent Active Learning 結論與建議

整理日期：2026-07-12  
範圍：VisualLatent 與 `C:\code\claude\ANnoTation`  
狀態：討論與產品規劃建議。M9 的 `pool_registry`／`round_ledger` 純邏輯核心與單元測試已完成；GUI 接線與 E2E 尚未完成。本次只修文件，不修改產品功能。

## 核心結論

VisualLatent 現在不缺分析功能，真正的問題是 Active Learning 尚未形成一條完整、可追溯的工作鏈：

```text
定義問題
→ 凍結候選池
→ 選出值得標註的樣本
→ 說明為何選擇
→ 送到 ANnoTation
→ 標註、審查與裁決
→ 將結果持久讀回
→ 建立新資料版本
→ 評估本輪改善
→ 決定下一輪或停止
```

目前主要斷點位於「送出之後」：批次狀態、責任人、標註讀回、資料版本、模型評估與下一輪之間沒有共同的 round lineage。

因此，現階段優先工作不應是增加新頁面或更複雜的選樣演算法，而應先建立：

1. 穩定的候選樣本身分與資料契約。
2. 將已完成的 Pool／round 純邏輯核心接入 GUI、送標與 read-back 流程。
3. 可持久化、可稽核的標註讀回。
4. User、領域專家、標註者與 CV 工程師的明確責任。
5. 每一輪可比較的成效與停止依據。

## 平台層補強結論（2026-07-19）

後續平台策略補強稿帶來的主要新價值，不是再增加一批分析頁，而是補上跨情境、跨版本、跨團隊的治理層。完整差距分析見 [08_平台概念差距分析.md](08_平台概念差距分析.md)。

目前判定：

- S1／S2／S3、embedding、相似搜尋、coverage／drift 等能力已有局部基礎，但尚未形成統一平台契約。
- **Business Risk、Active Learning Promotion Gate、Backbone 遷移、Patch 儲存分層、Platform Owner／Governance Board** 是現有結論真正缺少的重要概念。
- Embedding Registry 與 Dataset Audit 值得成為下一個平台驗證階段，但不能取代目前可信 read-back、資料版本與 lineage 的 P0；應建立在這些地基之上。
- Similar Case Search 不需重做檢索核心，真正缺口是 tool／recipe／maintenance／root cause 關聯與可衡量的工程 ROI。

建議順序調整為：先完成可信閉環與責任人決策，再做最小 Registry／Audit，接著以 offline replay／shadow mode 驗證選圖策略，最後才投入 backbone migration、storage policy 與跨團隊平台治理。

## 頁面合併結論

### 不建議硬合併的頁面

Visualize Embeddings、完整度熱力圖與瑕疵偵測都能選樣，但三者處理的問題不同：

- Visualize Embeddings：探索群聚、離群、相似、重複與資料策展。
- 完整度熱力圖：找 representation gap、稀疏區與屬性缺格。
- 瑕疵偵測：建立 normal bank、計算 anomaly risk、挑選高風險樣本。

它們的操作單位可能分別是原圖、物件、bbox、crop 或 anomaly patch。直接合併 UI 容易產生索引錯置與使用者混淆。

建議保留三個工作介面，但共用：

- `sample_id / object_id / bbox / mask`。
- 去重與已送標檢查。
- hybrid sampling。
- selection reason。
- round/pool 狀態。
- 送標與 read-back 契約。

### 建議合併或移轉的功能

| 現有功能 | 建議處置 |
|---|---|
| 組考卷 | 多人派件與重複標註移到 ANnoTation；LV 保留 agreement/kappa 分析 |
| 灰帶覆核 | 併入「標註迴圈」的 adjudication queue，不恢復獨立頂層頁面 |
| 評估 | 併入每一輪 round report，顯示 recall、FN、overkill、underkill 與標註效益 |
| 匯出清單／購物車／候選清單 | 統一稱為「候選清單」；提供「送標」與「建立資料版本」兩個明確動作 |
| 📥 標註回饋 | 擴建為「標註迴圈」中樞，不新增第七個頂層頁面 |

## VisualLatent 與 ANnoTation 的責任邊界

### VisualLatent

- 定義本輪資料與模型問題。
- 建立 pool snapshot。
- 計算 anomaly、uncertainty、coverage、diversity 與 drift。
- 選樣並提供可理解的 selection reason。
- 建立標註批次。
- 驗證 read-back 並建立資料版本。
- 重訓、評估與產生下一輪建議。

### ANnoTation

- 顯示 Round Inbox 與任務說明。
- 分派 annotator、reviewer 與領域裁決者。
- 執行分類、bbox、polygon、mask 與 attribute 標註。
- 支援 uncertain、skip、needs-expert 與退回原因。
- 執行 review、adjudication 與 QA gate。
- 只提交目前 handoff 的結果，不替 LV 決定是否套用到訓練資料。

## ANnoTation 的重要問題

### P0：匯出可能錯關其他 handoff

目前的概念風險是：匯出一個批次時，可能把所有尚未完成的 VisualLatent handoff 一起標成 `read_back`。

正確語意應為：

```text
目前 manifest
→ 對應唯一 handoff_id
→ 完成標註
→ 完成 review
→ 提交這個 handoff
→ LV 驗證
→ LV 明確 applied
```

匯出檔案不代表已審查，也不代表已套用到資料集或模型。

### 待查證的概念風險：Review 可能有兩套真相

已確認 `.review.json` sidecar 與 domain core／DB `ReviewDecision` 都存在，但尚未完整追完讀寫與同步資料流，因此目前不能定性為已發生的 bug。立案前應先確認實際 canonical source、衝突時的優先序與是否存在雙寫；若兩者都能獨立決定狀態，再收斂為單一真相。方向上建議 DB/core 作 canonical truth，sidecar 只作交換 artifact。

### P1：Detection read-back 不完整

若只讀第一個 shape label，無法支援多框、多物件或 polygon 任務。Detection Active Learning 必須回收全部 geometry、attribute 與 review decision。

## 半導體工業檢測的北極星

不應以 overall accuracy 作為主要目標。建議北極星為：

> 在 critical defect recall 與 escape 上限不退步的前提下，以最少的專家時間降低 overkill，並確保每個決策可追溯、可重現、可回退。

## 優先半導體情境

1. **AOI／ADC 複判與 nuisance 壓降**：降低大量 false reject 與人工 review 負擔。
2. **極端不平衡與稀有缺陷**：從大量正常 die 中找出少量 killer defect。
3. **新 defect mode 發現**：離群→相似群聚→領域專家裁決與建類。
4. **Golden／normal bank 維護**：避免污染，支援版本、簽核與 rollback。
5. **Tool、chamber、recipe domain shift**：設備保養、換 recipe 或換機台後的模型退化。
6. **Wafer map systematic pattern**：edge、ring、scratch line、cluster 等空間事件。
7. **封裝與多視角檢測**：bump、bond、underfill、package crack、X-ray/SAM 等。
8. **模型 escape 與客訴追溯**：找回當時模型、threshold、recipe、資料與標註版本。
9. **標註歧義與專家分歧**：將 uncertain 樣本送 adjudication，而不是強迫標註者猜測。

## 半導體必要 metadata

以下資訊必須成為正式欄位，不能只寫在資料夾名稱：

- `product_id, lot_id, wafer_id, die_x, die_y, unit_id`。
- `process_step, layer, recipe_id, tool_id, chamber_id, station_id`。
- `inspection_tool, modality, magnification, view_id, timestamp`。
- `defect_code, severity, nuisance/real, disposition, taxonomy_version`。
- `model_version, bank_version, threshold_version, acquisition_reason`。

抽樣、資料切分與驗收至少應以 lot／wafer 為群組，避免同一 wafer 的鄰近 die 同時出現在訓練與測試資料中。

## 建議的第一個產品切片

第一階段應選一條真實、範圍清楚的 ADC 分類複判流程：

```text
建立 lot-aware 未標池
→ anomaly + uncertainty + diversity 選樣
→ 帶 task/reason 送 ANnoTation
→ 標 real / nuisance / defect type / uncertain
→ review 與專家裁決
→ 持久 read-back
→ 建立 immutable dataset version
→ 比較 overkill / underkill / review reduction
→ 人工決定下一輪
```

這條流程能最早驗證 VisualLatent 與 ANnoTation 的責任邊界，也最接近半導體工業檢測的實際價值。
