整理日期：2026-07-19（同日稍後合併第二份獨立分析＋逐條程式碼查核，見文末「2026-07-19 更新」；

輸入：使用者提供的「Semiconductor Visual Intelligence Platform Strategy」補強稿  
範圍：只分析概念與優先序，不批准開發、不修改產品功能。

## 結論

附件中確實有現有產品檢視尚未完整納入的重要概念，但不能把它們全部判定為「新功能」。較準確的判斷是：

- VisualLatent 已有不少**局部能力**：S1／S2／S3 訊號、embedding、patch feature、相似度搜尋、coverage／drift 選樣、pool／round lineage。
- 現有 `00_結論與建議.md` 已較完整處理**單一 Active Learning 回合如何可信閉環**。
- 附件真正新增的是**跨情境、跨版本、跨團隊的平台治理層**：共用 Registry、可重複執行的 Audit、策略 Promotion Gate、Backbone 生命週期、儲存成本政策與平台責任人。

因此最重要的補強不是再新增一批頁面，而是把「已有演算法元件」提升成「有版本、基線、放行條件、成本邊界與責任歸屬的共用能力」。

## 最重要的五個新增概念

### 1. Business Risk 必須獨立於模型分數

S1／S2／S3 描述「模型與資料哪裡不可靠」，Business Risk 描述「如果判錯，代價多大」。兩者不能混為同一個 confidence。

建議概念式為：

```text
候選優先度
= 概念風險（S1）
+ 覆蓋風險（S2）
+ 模型風險（S3）
+ 業務風險（由 Scenario／Quality Owner 定義）
- 重複性與已處理狀態
```

業務風險至少要能表達 defect severity、escape impact、客戶／產品關鍵性與暫時性管制狀態。它不能由 CV 工程師從 embedding 自動推導，也不能只用類別頻率代理。

### 2. 選圖策略也需要 Promotion Gate

現有 round report 是評估「本輪結果」，附件補上的是評估「是否應替換選圖策略」。這是不同層次，應保留：

1. **Offline replay**：在相同已知標註池與 budget 下，比較 random、confidence、diversity、novelty 與整合策略。
2. **Shadow mode**：新策略產生候選但不取代正式工作流，觀察 hard-case 命中、重疊、domain 集中與高風險群漏失。
3. **Promotion／rollback**：門檻需同時包含效益與 guardrail；不能只看平均 recall。

最小 gate 應包含：固定標註量的 per-class／critical recall、duplicate labeling、跨 tool／recipe coverage、高風險案例命中率與專家時間。若資料版本、候選池或標註政策不同，策略間結果不可直接比較。

### 3. Embedding Registry 不是另一個 pool registry

兩者名稱接近但責任不同：

| Registry | 管理對象 | 核心問題 |
|---|---|---|
| 既有 `pool_registry` | 樣本在 Active Learning 中是否 sent／labeled／excluded | 這筆樣本處理過了嗎？ |
| 建議的 Embedding Registry | 某個 image／ROI 由哪個 backbone、preprocessing 與資料版本產生何種 embedding | 這個向量是什麼、能否比較、如何重算？ |

Embedding Registry 至少需要內容身分、資料／metadata 引用、entity level（image／ROI／object）、backbone version、preprocessing version、向量維度、產生時間、狀態與 storage class。第一階段不必先承諾線上向量服務。

### 4. Backbone 相容性檢查不等於生命週期治理

現有設計能防止不同 DINO variant 或 resolution 的向量被錯誤混用，這是正確地基；但仍缺少：

```text
Candidate
→ 固定 benchmark
→ active／golden／critical set 重算
→ 新舊雙寫
→ retrieval 與 downstream 比較
→ 人工 promotion
→ 分批／按需遷移
→ 舊版退役或 rollback
```

在只有一個正式 backbone 時可先記錄為治理設計；準備導入 DINOv3、內部 SSL 續訓或領域專用 encoder 時，必須先成為硬 gate。

### 5. 平台治理是現有 RACI 的上一層

現有角色表已回答單一 scenario 中誰定義 defect、誰標註、誰裁決、誰發布模型；仍需補一個跨 scenario 層：

- Platform Team：Embedding Registry、共用 schema、benchmark、storage、security、SLA 與成本。
- Scenario Owner：defect definition、threshold、business risk、acceptance criteria 與 production decision。
- Fab／Process Owner：metadata 正確性、製程解釋、quality impact 與異常處置。
- Governance Board：重大 schema／backbone 變更、跨廠標準、fork 例外與版本退役。

「團隊可以建立 scenario configuration，但不能無治理地 fork 核心 schema 與版本規則」是合理方向；是否允許多 backbone 應由 benchmark 與影像領域差異決定，而不是先規定全公司只能有一個 encoder。

## 優先序裁決

附件提出「P0 只做 Embedding Registry 與 Dataset Audit」，若是全新平台提案，這個排序合理；但對目前 VisualLatent 現況不能原樣套用，因為已有未完成的送標／read-back／dataset lineage 工作。若先建立 Registry／Audit 而沒有可信的身分、版本與讀回閉環，只會產生另一套無法驗證來源的分析資產。

建議改成四段：

### P0-A：完成可信閉環與擁有權決策

- 〔查核修正〕read-back persistence **已完成**（M18 `readback_store`，2026-07-12：gate 11 綠＋E2E 3/3，
  append-only 變更日誌＋sha256 覆蓋層，見 ROADMAP）。本項剩餘工作為 immutable dataset version 與 lineage。
- 決定 Business Risk、Platform Owner、Scenario Owner 與 promotion 簽核者。
- 固定 entity identity 與最小 metadata；這是 Audit 和 Registry 的共同前置。

### P0-B：低風險平台驗證

- 以既有 embedding／cache 為來源建立最小 Embedding Registry 契約，不先做大型線上服務。
- 對一個 ADC scenario 產生可重現 Dataset Audit。
- 首輪只承諾可量化結果：duplicate／leakage、label conflict、coverage gap、outlier 與 training-production distance。

### P0.5：使用者價值與策略驗證

- 把既有 Similar Search 接上工程 metadata、處置與 ROI。
- 建立 Offline replay；通過後才進 shadow mode，再決定是否 promotion。

### P1：規模化治理

- Patch storage tier、retention、重算與成本預算。
- Backbone benchmark、雙寫、lazy migration、rollback 與 deprecated policy。
- Security／access control、SLA、跨團隊 schema 變更與 fork 例外流程。

## 現階段不應誤判為已完成

- 有 embedding cache，不代表已有 Embedding Registry。
- 有重複／洩漏或 coverage 功能，不代表已有可重現、可簽核的 Dataset Audit。
- 有 round report，不代表 acquisition strategy 已通過 replay／shadow／promotion。
- 有 model／bank 相容性檢查，不代表已有 backbone migration。
- 有 scenario RACI，不代表已有平台 owner 與跨團隊治理。
- 有相似度排序，不代表已有以 root cause time 或 review reduction 衡量的 Similar Case Search 產品。

## 建議保留的主管敘事

附件最值得保留的定位是：

> 第一階段不是再做一個 AI 模型，而是建立能看懂影像資料品質、覆蓋風險與模型盲點的共同基礎。

但在 VisualLatent 的實際路線圖中，前面應補一句前置條件：

> 先確保每一次選樣、標註、裁決與資料版本都可追溯，再把這條可信閉環升級成跨情境共用的平台能力。

這樣既保留附件的平台野心，也不會跳過目前產品最真實的可靠性缺口。

## A. 補充視角：單機尺度 vs 平台尺度（A／B／C 分類）

平台補強稿是**組織級戰略**；VisualLatent 今天是**單機工程師工作台**。概念應分三類，
避免被平台語彙帶著過度設計：

- **A 類（已有，名字不同）**：−重複性（`hybrid_sampler` FPS＋`pool_registry` sha256 永不重複送標）、
  Drift（Compare＋M10 監看）、Unknown Discovery（M3/M6 閘控級聯）、監看佇列「建議不取代」。
- **B 類（真缺、單機尺度就有價值）**：即本檔 P0-A～P0.5 的主體。另補一項兩檔都認定的缺口：

- **C 類（真缺、但平台／多人尺度才需要，現在做是過度設計)**：
  Governance Board／SLA／SDK／access control（單人工具無此問題；屆時 U-Net 開發治理經驗可平移）;
  backbone 雙寫＋lazy migration（單機「鎖版本、要換就重算」更便宜更不易錯；C9 查核證實
  版本拒載地基紮實）;Frozen vs SSL 續訓四組對照（是「要不要養訓練管線」的組織決策前置，
