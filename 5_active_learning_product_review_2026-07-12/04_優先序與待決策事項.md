# 優先序與待決策事項

本文件是產品建議，不代表已批准開發。

## P0：先閉環，再談更聰明的取樣

1. **持久 read-back 與變更日誌**：標註結果不能只作用於 session；需留下 old/new、annotator、時間、理由與 schema 版本。
2. **M9 GUI 接線與 E2E**：`pool_registry`（9 tests）與 `round_ledger`（8 tests）的純邏輯核心已完成；剩餘工作是接入送標／📥 read-back／round timeline，並補真實 E2E，不是從零開發。
3. **批次狀態與責任顯性化**：送出、已領取、標註中、已提交、驗證失敗、已套用不能混為「read back」。
4. **清除幽靈流程**：所有仍指向已隱藏組考卷／灰帶覆核／評估的文案應改為新的真實動線。
5. **半導體 metadata 最小 schema**：先決定 lot/wafer/die/tool/recipe/layer 如何帶入、驗證與傳遞。
6. **修正 handoff closeout 語意**：ANnoTation 每次只能提交目前 manifest 綁定的 handoff；export 不等於 reviewed 或 applied。
7. **追查 review truth**：已確認 DB/core 與 `.review.json` 兩種機制存在，但尚未證實實際分歧；先追完整資料流，再決定是否需要收斂。

## P1：讓每一批都可用、可評估

1. 統一候選 identity、bbox/mask、task、selection reason 與模型版本。
2. 瑕疵偵測第③步提供真正的送標動作，不讓使用者猜「加入購物車」是否等於送出。
3. Visualize 與 anomaly 共用 hybrid sampler／去重／配額，但各自保留 UI。
4. 將 hidden evaluation 併入 round report：per-class recall、FN gallery、overkill/underkill、標註成本與邊際增益。
5. ANnoTation 支援 uncertain/skip/escalate，並把 annotator、裁決者與 instruction version 送回。
6. Golden bank 建立版本、差異、血統與簽核流程。

## P2：降低認知負擔

1. 頁面與 caption 改成工作語彙：資料探索、資料覆蓋與補洞、瑕疵建模與挑樣、候選清單、標註迴圈。
2. 將「桶①、採礦池、H1–H5、偏 novelty」等內部詞彙改成可直接採取行動的說明。
3. Compare 結果可納入回合報告；不擴張成即時製程監控產品。
4. 顯示「系統為何沒有選另一張」：已標、已送、近重複、domain quota、品質不足等排除原因。

## 開發前需要 User／PO 決定

- 第一個目標任務暫定為 **ADC 影像分類複判**；若現場其實以 detection 為主，需重新調整 shapes read-back 優先序。
- 哪個資料層是 pool 的唯一單位：原圖、defect crop、bbox object、die，或一組多視角 unit？
- 正式角色有哪些：複判員、領域工程師、QA、CV；誰能裁決 taxonomy、golden bank 與模型 gate？
- 正式資料來源是否能提供 lot/wafer/die/tool/recipe；若不能，允許以哪種 sidecar manifest 補足？
- ANnoTation 是否是唯一標註入口；是否要讓 handoff 成為其正式 task queue，而非資料夾旁路？
- 評估門檻以什麼為主：underkill、overkill、per-class recall、review reduction、top-K hit rate；由誰簽核？

## 已由既有約束決定

- Read-back 不得直接寫回原始 label。依 `CLAUDE.md`，App 絕不寫使用者資料集；採 `.lv_cache` overlay＋append-only log，再由明確動作發布 immutable dataset version。
- M9 不需重做核心；排程從 GUI 接線與 E2E 開始。

## Gate 前置治理

`python verify/gate.py pool_registry` 目前會在 9 個測試通過後仍回 RED，因 `3_Architect_Design/10_gt_pred_diff.md` 在既有 snapshot 後發生雜湊變更。未找到對應的核准紀錄，因此不可直接用 `--snapshot` 掩蓋；先由 PO／Architect 確認並補 ROADMAP 決策日誌，再更新 baseline。

## 明確不建議

- 不為了頁數少而合併不同索引空間的互動畫面。
- 不在尚未可靠讀回前投入複雜 acquisition function；否則只會更快產生不可追溯的批次。
- 不讓 CV 工程師單獨決定 defect taxonomy、正常判準或生產停止門檻。
- 不讓整體 accuracy 掩蓋稀有缺陷漏檢。
- 不以資料夾名稱代替生產 metadata 與資料血統。

## 建議的第一個產品切片

先選一條單純但真實的 ADC 分類複判流程：

```text
凍結一個 lot-aware 未標池
→ anomaly / uncertainty / diversity 挑一批
→ 帶 reason 與 task 送 ANnoTation
→ real / nuisance / defect type + uncertain
→ 持久 read-back 與裁決
→ 建立新 dataset version
→ 比較 overkill / underkill / review reduction
→ 決定下一輪
```

這個切片能同時驗證兩個系統的責任邊界，也最接近半導體檢測的實際採購價值。
