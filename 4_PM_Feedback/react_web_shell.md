## 完成判準

AC2、AC3、AC6 須以真實權重和可見 UI 通過；AC1、AC4、AC5 可先由 deterministic 單元／API 測試覆蓋。AC1–AC5 已有本機證據；固定 DINOv2-small 的直接 worker 路徑亦已在 Windows ARM64 通過。AC6 的 NativeApp picker、folder grant 與 worker lifecycle 尚未驗，因此 `LV-WEB-01-IC-01` 及 M24 不能標為完成。任何 `skip`、fake backend、截圖-only、HTTP-only 或模型健康檢查均不得將此 case 標為完成。

## 既有操作旅程與 React case inventory

本表依 2026-11-01 LV 工具列、scripts/app.py 的 UI 分流、使用指南、已存在的 UI／E2E 測試與本機來源 checkout 的誤逮案件規格盤點，共整理 44 個可驗收 journey。每列是一個可完整操作與回讀的 journey；控制項數量不等於 use case 數量。

Legacy 測試只作為 Streamlit 行為錨點，不算 React 通過證據。React case 必須用固定輸入、固定模型、可見 UI 操作重跑；檢查顯示結果、領域數值、檔案輸出、跨工具 handoff、資料夾副作用及重開後狀態。LV-WEB-01-IC-01 有 AC1–AC5 本機證據；IC-02 有 deterministic API/core 覆蓋，仍須真實多模型與完整 UI parity。LV-WEB-02 的整圖與物件比較已有 fixture API／UI 局部證據，真實模型與 Streamlit 數值 parity 未驗。標成「本機來源」的文件／測試存在於原 LV 使用者工作樹，但尚未併入本隔離分支，不得當成此分支的 CI 證據。

### Case 完成與證據規則

每個 React case 都要有固定 fixture 內容 hash、model/profile/weight 身分、同樣的操作序列及可比較輸出。輸出至少核對畫面內容與選取身分；有數值時核對領域指標與事先定義的容差；有下載時核對檔案內容；有保存時停止 worker 並以新 PID 讀回；最後比對來源資料夾前後 hash。缺檔、空資料、模型不可用及取消依原行為逐列覆蓋。

只有上表裡的旅程都有對應 React case、legacy 對照與可見 UI receipt 後，才能報告 parity。舊 Streamlit 測試、HTTP status、health check、單張截圖或 mock model 都不構成該旅程的 React 通過證據。隱藏路由、缺少固定 fixture 或只有本機未提交的 legacy 測試列為待釐清，不推定通過。
